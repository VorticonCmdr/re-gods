# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> **Evidence discipline.** This directory is a reverse-engineering target, not a source repo. Every claim in this project is tagged with how it was established. Do not add unverified claims — label unknowns `UNKNOWN_<identifier>` instead.
> `[PROVEN]` = verified by executing something (decompressed the bytes, ran the code, or traced it live under DOSBox).
> `[STATIC]` = read out of the binary (strings/disassembly) but **not** confirmed at runtime.
> `[WF]` = **produced by a subagent workflow and not yet re-read by the maintainer.** Plausible and adversarially reviewed, but nobody in this project has personally executed a check on it. That workflow's own error rate was demonstrably nonzero — fifteen of its findings were refuted on bytes by its own verifiers, and a histogram it reported was wrong. **Treat `[WF]` as a lead, not a fact, and promote it to `[PROVEN]` only by reading the bytes.**
> `[UNKNOWN]` = not established.
>
> **The DOSBox bridge is working** (mount `C:\Users\...\Gods`, launch with `gods`). The full launcher chain — `GODS.EXE` → `INTROV.EXE` → `GAME.EXE`, config parse, drive-check bypass, EXEC patching, overlay loads, first Table-2 asset open — has been traced live with `INT 21h` breakpoints and matches the static disassembly exactly, down to individual register values. See `docs/dynamic-trace-and-runtime-data.md`. The game renders and plays correctly through this path.

## What this is

A complete file dump of the DOS release of **GODS** (The Bitmap Brothers / Millennium Interactive, 1991/92) — raw floppy-disk contents, `GODS.INI` records "Version 1.0". 140 files, **no source code, build system, or tests**. There is nothing to build, lint, or test; treat all work here as software archaeology.

`READ.ME` (the game's own release notes) states SoundBlaster/Roland music and high-score/password saving work only when installed to hard disk, not from the low-density 3.5" floppy.

## Open questions

**Every registered `UNKNOWN_*` in this project is now closed.** The last one, `UNKNOWN_spike_base_crop_mechanism` (`docs/destructible-and-hazards.md`, the retracting-spike section), closed by reading a single 13-instruction helper (`FUN_1000_1AD6`) the prior pass had assumed but never actually checked: it never touches `CX`, so the sprite-id register feeding `GAME.EXE`'s `SI = 0x1e00 + spriteId*8` survives unchanged into the base draw call — provably the SAME address `VGA.EXE`'s own export-2 consumer (`VGA:0x1BDB`-`0x1BE8`) independently re-derives from the sprite id it's handed, closing the address-match the earlier pass could only narrow. The descriptor layout (`+2`=rows−1, `+4`=source offset, `+6`=source segment) makes the port's `pingpong+1`-rows-from-16-in geometry the literal arithmetic `GAME.EXE` executes, not just an empirical match. `UNKNOWN_189c_motion` and `UNKNOWN_189c_type_dispatch` (`docs/triggers-and-difficulty.md`, selectors 7–10 line-barriers) are now both CLOSED: the obstacle-type byte selects one of 12 behaviors — 8 "settle at one resolved target point and hold forever" variants, 2 "cycle forever between the record's points" variants (forward/backward), and a disable sentinel — cross-checked against all 8 shipped levels' own event tables (183 real dispatches: 148 settle, 7 cycle, 28 disabled) and against each level's plane-B/`ACT5` reachability (5 of the 7 shipped cyclers are real, reachable ping-pong barriers in worlds 1B/2A/2B; the other 2, an elaborate 4-point patrol variant in world 4, are placed but never wired to anything reachable — dead content, not a bug). `UNKNOWN_pgods_mus_cue_dispatch` is also CLOSED, live-confirmed in DOSBox: `PGODS.MUS` was never the per-world music file at all — real per-level music is `PGODSRL{A..G}.RL`, selected by patching a world-derived letter into `ROL.EXE`'s own embedded filename and re-opening it, driven by a one-byte "context id" `GAME.EXE` sends through sound export slot 12 (a bare `RETF` stub under every non-Roland driver, which is why `PGODS.MUS` — the file those drivers load instead — is never re-selected per level). Its one residual is also now resolved: an exhaustive call-site search (the original close checked three sites, not all seven that exist) found `PGODSRLG.RL`'s producer — it plays during the world-2/world-3 segments of the title screen's own attract-mode demo cycle (gated on a non-floppy install), and the search also corrected "a death/retry path" to what `FUN_1000_2c82` actually is: the title-screen menu loop, reached by dying as much as by booting. See `docs/open-questions-history.md` for the full closure history (dozens of items, each with its own resolution — several closed only as "authorial intent is unprovable in principle," which is this project's own standard for as-resolved-as-bytes-allow, not a loose end).

⚠️ **Correction: two more items were untracked, not closed — they are now.** `UNKNOWN_sublevel_b_entry_point` and the `joyl`-recording playback-termination question both lived as inline `UNKNOWN`/prose loose ends in `docs/dynamic-trace-and-runtime-data.md` and `docs/asset-formats.md` but were never promoted into `docs/open-questions-history.md`'s ranked list, so the "last registered open item" framing above missed them. Both are now CLOSED, `[PROVEN]` live in DOSBox this session (see ranked item 20 in that doc): the attract cycler's `joyg` segments force every world's sublevel from A to B via a dedicated double-load in `FUN_1000_2df1` before any gameplay tick runs (sublevel A is loaded but never actually played, for all three worlds alike — not "both sublevels in turn" as earlier prose had it), and `joyl` recordings, rather than staying menu-bound forever, provably do (for both `joyl1`/`joyl2`, as shipped) escape into real per-tick gameplay via some genuine menu selection — "BEGIN QUEST" or the password screen, not yet pinned down between the two — after which the same recording keeps driving that gameplay off the same buffer until it hits its own `0xFF` terminator, caught by the identical explicit sentinel check `joyg` already uses.

A third item, `UNKNOWN_189c_fresh_arm_index` (ranked item 21), was opened and CLOSED in the same later session: a disclosed gap left in `gods-web`'s own line-barrier cycling port (what the runtime `DI+5` point-index reads on a fresh arm, before `FUN_1000_78E9`/`0x790E`'s bump-and-wrap arithmetic) turned out to be answerable straight from the arm dispatcher itself — `CS:0x7665` unconditionally zeroes it on every arm, confirmed both by disassembling `CS:0x75FC`–`0x7679` in full and by a live DOSBox breakpoint catching `PLEV1A` record 2's own first-ever arm with the slot in its genuine "never-armed" state. `gods-web`'s `bump1Based(0, direction)` was already the correct arithmetic; it's now proven, not inferred.

A fourth, `UNKNOWN_189c_tick_placement` (ranked item 22), closed the cycling port's LAST disclosed gap: where `FUN_1000_767A` (the rescan loop) actually sits in `FUN_1000_006F`'s real per-tick call order. A plain `get_xrefs_to` on the rescan's own self-modifying gate address — never actually run by the pass that shipped the cycling port — resolves it outright: two unconditional callers, `FUN_1000_006F` at `CS:0x01F2` and the death driver `FUN_1000_09BB` at `CS:0x09C7`. `0x01F2` is one of the EARLIEST systems in the whole tick (before pickup, projectiles, the player, selector-2, entities, enemy shots, the line-hazard pool). `gods-web` had shipped it called near the END of the tick instead — the shipped placement was backwards, not merely unproven, though its death-sequence gating was already correct (verified with `acorn`, not assumed). Fixed, with a new static check (`tools/scope-check.mjs`'s `checkCallOrder`) that would have caught this class of ordering bug, which `vite build`, the invariant suite, and even an automated browser tab all fail to catch.

A fifth, `UNKNOWN_respawn_zone_table` (ranked item 23), RE-CLOSED an already-closed item with a corrected answer, live in DOSBox — user-reported: a world-1 death in `gods-web` respawns "near the initial starting point but too low ... and falls out of the screen." The earlier closure read the respawn arrival-zone table (`docs/camera-and-world-nav.md`) as 14 records and concluded a no-match falls back to entry 13's own real offset, `(-32,+48)`. Forcing a live world-1 death (writing `DS:0x192`/`0x19a` to 0, then reading `DS:0x17a`/`0x17c` after respawn) landed the hero at exactly the rounded spawn tile, zero offset — not `(-32,+48)`. The table is genuinely 15 records (90 bytes, not 84): the loop's own exit condition advances one record past entry 13 before falling through, to a real, deliberate all-zero sentinel the earlier pass never transcribed. `PLEV1A` has no `0xFF` arrival marker near its own static spawn, so every world-1 death took the wrong 14-entry fallback, landing at row 62 of a 64-row map where the hero's own 48px ground probe reads out of bounds — exactly the reported bug. Fixed in `gods-web/src/game/death.js` and the doc, corrected in place.

A sixth, `UNKNOWN_level_palette_source` (ranked item 24), CLOSED — and, like item 23, the closure corrects rather than confirms an earlier reading. User-reported: "the background of the second part of the city isn't red but blue in dosbox." Intercepting the real `INT 10h AX=1012h` DAC-install call for a clean world-1 load found palette slots 2–15 genuinely come from `PLEVEL1A.PI1`, but slots 0/1 do not — the file holds a gray/red pair (`0x0333`/`0x0400`) where the live DAC holds black/blue (`0x0000`/`0x0247`) instead, identical for both 1A and 1B. An exhaustive search of every shipped file's own decompressed bytes found the live value in none of them; the override is written by code this pass could not trace to a source file. Fixed in `gods-web` with a `PALETTE_SLOT01_OVERRIDE` table, honestly scoped to world 1 only — worlds 2–4 were not reached live in this pass (`Begin Quest` always loads world 1, and the sublevel-B attract-forcer used for item 23/earlier closures does not select a different world), so their own files' slots 0/1 are disclosed as unconfirmed rather than guessed at.

`UNKNOWN_password_grid_layout` — **CLOSED**, see `docs/dynamic-trace-and-runtime-data.md`'s title-screen section. The item's own prior framing was wrong about *why* it was open: it assumed the geometry could only come from disassembling `FUN_1000_2eb0`'s own draw routine, but a live DOSBox session (booting straight through `GODS.EXE`→`INTROV.EXE`→`GAME.EXE`, no breakpoints needed) just looked at the screen instead. The widget is an **8-column x 5-row, 40-cell grid**: rows 1-3 are `A-H`/`I-P`/`Q-X`, row 4 is `Y Z . <space> 0 1 2 3`, row 5 is `4 5 6 7 8 9` then a left-arrow erase icon then a distinct circular confirm icon (neither a `PSMLFNT` glyph — their own sprite source wasn't chased down). This cross-validates exactly against this project's own EARLIER finding in the same doc section (moving the cursor "from index 34 to 39" via "5x KBD_right" during a hiscore-name completion): row-major index 34 is row 4 col 2 (the `6` cell) and index 39 is row 4 col 7 (confirm), precisely 5 columns apart — the SAME session's own byte-level cursor-index evidence and THIS session's own visual-grid evidence pin each other down independently. Also closed as a side effect: the menu's own option-1 text is `"ENTER PASSWORD"` (no `"A"`) — a DIFFERENT string from the password screen's own title, `"ENTER A PASSWORD"` (1ffd:eb96) — and the selected menu option is flanked by inward-pointing arrows on both sides (`> BEGIN QUEST <`), not a single leading marker. `PBACKSCR.PI1`'s bitmap being blitted full-screen as the title/menu backdrop is now `[PROVEN]` too, not merely the "palette feeds a fade helper" lead `docs/drivers-and-memory.md` previously had — see that doc's own updated entry. Two loose ends, both genuinely minor: the erase/confirm icons' own sprite source is unlocated, and this pass's read of the grid's ambiguous row-4 middle cell (obscured by the skull artwork in every screenshot taken) rests on the established alphabet ordering (`.` then space) rather than a clean, unobstructed pixel read.

`UNKNOWN_chest_key_surplus` (world 2 half) — **CLOSED**, see `docs/consumables-and-treasure.md`. The prior pass only checked static object placement and trigger *conditions* referencing key 23; it never checked trigger *actions* that spawn objects. A fresh census of all 800 records' action-verb-0 (spawn object) entries found exactly one iron-chest spawn and one key-23 spawn in the whole game — `PLEV1A` triggers #3/#4, 25px apart, gated on the identical three conditions (two levers plus an event check). So key 23 / iron chest 16 has a real, designed, shipped use: a lever-puzzle-gated dynamic spawn in world 1 — which the earlier static-placement census could never have found. Checked four independent ways (static census, condition census re-derived this session, the new action-spawn census, and the separate "using a key consumes it" path at `CS:0x3AEB`, shown to be a subset of the condition census rather than a new avenue), world 2's two key-23 pickups have zero consumers anywhere in the shipped game. Why they were placed at all is retired as unprovable in principle, the same disposition as the two items below.

`POBJECTS` category 5's enum **meaning** — **CLOSED**, see `docs/destructible-and-hazards.md`. The prior search looked for a `CMP CX,<sprite>` chain (category 4's own dispatch shape) and missed category 5's actual mechanism: a category-level branch, one step earlier in the same object-array walker, into a sprite-id-keyed **jump table** (`CS:0x19BA`, `DS:0xdfb0`, 13 entries + a default). All six reachable handler bodies were read to their terminating jump this session: every one does nothing but resolve a draw position, optionally animate a 4-frame table (the same position-phased, globally-ticked idiom already documented for the destructible spike's overlay) or add a second fixed tile, then call a masked-sprite-blit graphics export (exports 1/2, already characterized in `docs/drivers-and-memory.md`). No hero state, health, inventory, score, damage grid, or trigger is referenced anywhere in the dispatch. A fresh map census also found 12 of the 22 types genuinely placed in shipped levels (mostly world 2), overturning the earlier "as plausible a candidate for never-instantiated filler" framing. Category 5 is purely visual background scenery, some of it self-animating.

`UNKNOWN_e4e2_displacement_drift` — **CLOSED**, see `docs/combat-and-projectiles.md`. A prior pass wrongly filed this as living inside the dead `UNKNOWN_tag_fd` path with "zero port impact"; a fresh full disassembly of both found-handlers (`CS:0xE4E2`–`0xE5E2`) this session showed neither loop returns on a hit — both scan to the end of their tick budget regardless — so the register-reuse drift (one register doing double duty as hit-counter and displacement-cursor step) fires on any ordinary two-hit scan, which the game's own grid-stamp footprint sizes make routine. But commonness and severity are inverted from the naive read: a single compact footprint's two hits land on *nearby* scan ticks, drifting the read by only 1–2 bytes (small misalignment); the large drift (up to 47 of the table's 192 bytes, bounded statically, never out of bounds) needs two hits far apart in scan order — the rarer shape, not the common one. Authorial intent is retired as unprovable in principle, not left pending — it's a question about the missing author's state of mind that no further bytes can answer.

`UNKNOWN_hunter_key_intent` — **CLOSED**, see `docs/combat-and-projectiles.md`. A prior pass mis-stated its own evidence as a minimum-scan ("homes on the lowest computed sprite id"); a fresh disassembly of `CS:0x9E36` this session showed it's a **maximum**-scan instead (seeded at `0xFFFF`, replaces only on a strictly larger key — the seed alone is structural proof of the intended direction, since a minimum-scan seeded there could never select anything). That correction resolves the item's original question: the already-documented post-hit key zero-out (disqualifying the just-hit target from being re-picked) only composes correctly with a maximum-scan — under the old, wrong minimum-scan reading it would have been self-defeating (the zeroed target would win every future comparison instead of losing). Seed-plus-side-effect together are stronger evidence of deliberate, finished design than "no dead arithmetic" alone. What can't be recovered from bytes is *why* sprite id specifically was chosen as the ranking key — retired as unprovable in principle, the same disposition as the item above.

⚠️ **A seventh untracked item, `UNKNOWN_random_mixer` (ranked item 25), is now CLOSED, `[PROVEN]` live in DOSBox** — same shape as items 20-22 above: it never had a registered entry in `docs/open-questions-history.md`, only an inline TODO in `gods-web/src/game/random.js` ("the MIXER is NOT ported"), where the port's random table came from a placeholder xorshift instead of `FUN_1000_2375`. Full disassembly plus a flag-flow trace of every call site prove the mixer is a pure 16-bit-seed function for the table generator's own 258 calls (`CF_in=0` at every one, each preceded by an `XOR`/`OR`/`CMP`/`AND` that clears it). Live-captured the real entry seed at `FUN_1000_37f6`'s entry (`[0x122]=0x6189`, live segment resolved by a `mem_scan` byte-signature match rather than trusted from an arbitrary pause) and the resulting 512-byte table; the disassembled algorithm reproduces it byte-for-byte from that seed. A genuine, newly-found property of the original: any seed `< 128` degenerates into a pure doubling sequence for several draws (the high byte being 0 collapses the whole `RCR`/`XOR` chain), narrow enough that a live wall-clock seed almost never hits it but common enough that three of `gods-web`'s own tests — seeded with small constants for readability — were quietly relying on its low diversity. Fixed in `gods-web/src/game/random.js` (`mix16()`, exact) and `src/verify/checks.js` (a live-capture regression check plus the three affected tests re-seeded/stubbed). See `docs/camera-and-world-nav.md`'s *Randomness* section and `docs/open-questions-history.md` ranked item 25 for the full writeup.
