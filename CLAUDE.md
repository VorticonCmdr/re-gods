# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> **Evidence discipline.** This directory is a reverse-engineering target, not a source repo. Every claim in this project is tagged with how it was established. Do not add unverified claims — label unknowns `UNKNOWN_<identifier>` instead.
> `[PROVEN]` = verified by executing something (decompressed the bytes, ran the code, or traced it live under DOSBox).
> `[STATIC]` = read out of the binary (strings/disassembly) but **not** confirmed at runtime.
> `[WF]` = **produced by a subagent workflow and not yet re-read by the maintainer.** Plausible and adversarially reviewed, but nobody in this project has personally executed a check on it. That workflow's own error rate was demonstrably nonzero — fifteen of its findings were refuted on bytes by its own verifiers, and a histogram it reported was wrong. **Treat `[WF]` as a lead, not a fact, and promote it to `[PROVEN]` only by reading the bytes.**
> `[UNKNOWN]` = not established.
>
> **The DOSBox bridge is working** (mount `C:\Users\...\Gods`, launch with `gods`). The full launcher chain — `GODS.EXE` → `INTROV.EXE` → `GAME.EXE`, config parse, drive-check bypass, EXEC patching, overlay loads, first Table-2 asset open — has been traced live with `INT 21h` breakpoints and matches the static disassembly exactly, down to individual register values. See `docs/dynamic-trace-and-runtime-data.md`. The game renders and plays correctly through this path.

## What this is

A complete file dump of the DOS release of **GODS** (The Bitmap Brothers / Millennium Interactive, 1991/92) — raw floppy-disk contents, `GODS.INI` records "Version 1.0". 140 files, **no source code, build system, or tests**. There is nothing to build, lint, or test; treat all work here as software archaeology.

`READ.ME` (the game's own release notes) states SoundBlaster/Roland music and high-score/password saving work only when installed to hard disk, not from the low-density 3.5" floppy.

## Open questions

⚠️ **A `[PROVEN]`-tagged claim about SFX pitch was REFUTED live this session — read `docs/drivers-and-memory.md`'s own corrected entry before trusting anything about the OPL2 SFX path.** The claim was that this class of sound effect "genuinely has no pitch of its own" and sounds at whatever frequency its OPL2 channel already holds. It does have pitch: each of the 70 SMF blobs in `PGODS.MUS` is a complete little MIDI sequence, and the `FF 7F` TAG=1 instrument metas are tick-positioned and channel-bound. Caught by breakpointing the same register-write primitive the original captures used, but with a CONDITION on the register number instead of stopping on the first hits: `AH=0xB0, AL=0x3E` (key-on, block 7) preceded by `AH=0xA0, AL=0x23` decodes to 3319.7 Hz = **MIDI note 104.00**, exactly blob 25's own single note. The original captures each continued ~17 times — the synchronous instrument-load burst — and stopped before the 50 Hz sequencer tick that plays the notes. **The methodological lesson, which generalizes past this one item: "every write was logged and none was an X" is only as strong as the window the logging covered, and that window was never stated as a limit.** A second, independent error was found in the same area: `gods-web` had the total-level substitution sign-inverted (`0x3F − rec[+8]` where the correct un-scaled value is `rec[+8]` itself), which made quiet instruments blare and loud ones near-silent. Both are fixed and the port now plays the real sequences through a measured OPL2 core; see that doc and `gods-web/src/audio/opl2-core.js`.

**Every registered `UNKNOWN_*` in this project is now closed.** The last one, `UNKNOWN_spike_base_crop_mechanism` (`docs/destructible-and-hazards.md`, the retracting-spike section), closed by reading a single 13-instruction helper (`FUN_1000_1AD6`) the prior pass had assumed but never actually checked: it never touches `CX`, so the sprite-id register feeding `GAME.EXE`'s `SI = 0x1e00 + spriteId*8` survives unchanged into the base draw call — provably the SAME address `VGA.EXE`'s own export-2 consumer (`VGA:0x1BDB`-`0x1BE8`) independently re-derives from the sprite id it's handed, closing the address-match the earlier pass could only narrow. The descriptor layout (`+2`=rows−1, `+4`=source offset, `+6`=source segment) makes the port's `pingpong+1`-rows-from-16-in geometry the literal arithmetic `GAME.EXE` executes, not just an empirical match. `UNKNOWN_189c_motion` and `UNKNOWN_189c_type_dispatch` (`docs/triggers-and-difficulty.md`, selectors 7–10 line-barriers) are now both CLOSED: the obstacle-type byte selects one of 12 behaviors — 8 "settle at one resolved target point and hold forever" variants, 2 "cycle forever between the record's points" variants (forward/backward), and a disable sentinel — cross-checked against all 8 shipped levels' own event tables (183 real dispatches: 148 settle, 7 cycle, 28 disabled) and against each level's plane-B/`ACT5` reachability (5 of the 7 shipped cyclers are real, reachable ping-pong barriers in worlds 1B/2A/2B; the other 2, an elaborate 4-point patrol variant in world 4, are placed but never wired to anything reachable — dead content, not a bug). `UNKNOWN_pgods_mus_cue_dispatch` is also CLOSED, live-confirmed in DOSBox: `PGODS.MUS` was never the per-world music file at all — real per-level music is `PGODSRL{A..G}.RL`, selected by patching a world-derived letter into `ROL.EXE`'s own embedded filename and re-opening it, driven by a one-byte "context id" `GAME.EXE` sends through sound export slot 12 (a bare `RETF` stub under every non-Roland driver, which is why `PGODS.MUS` — the file those drivers load instead — is never re-selected per level). Its one residual is also now resolved: an exhaustive call-site search (the original close checked three sites, not all seven that exist) found `PGODSRLG.RL`'s producer — it plays during the world-2/world-3 segments of the title screen's own attract-mode demo cycle (gated on a non-floppy install), and the search also corrected "a death/retry path" to what `FUN_1000_2c82` actually is: the title-screen menu loop, reached by dying as much as by booting. `UNKNOWN_e4e2_displacement_drift` — **CLOSED**, see `docs/combat-and-projectiles.md`. A prior pass wrongly filed this as living inside the dead `UNKNOWN_tag_fd` path with "zero port impact"; a fresh full disassembly of both found-handlers (`CS:0xE4E2`–`0xE5E2`) this session showed neither loop returns on a hit — both scan to the end of their tick budget regardless — so the register-reuse drift (one register doing double duty as hit-counter and displacement-cursor step) fires on any ordinary two-hit scan, which the game's own grid-stamp footprint sizes make routine. But commonness and severity are inverted from the naive read: a single compact footprint's two hits land on *nearby* scan ticks, drifting the read by only 1–2 bytes (small misalignment); the large drift (up to 47 of the table's 192 bytes, bounded statically, never out of bounds) needs two hits far apart in scan order — the rarer shape, not the common one. Authorial intent is retired as unprovable in principle, not left pending — it's a question about the missing author's state of mind that no further bytes can answer.

`UNKNOWN_hunter_key_intent` — **CLOSED**, see `docs/combat-and-projectiles.md`. A prior pass mis-stated its own evidence as a minimum-scan ("homes on the lowest computed sprite id"); a fresh disassembly of `CS:0x9E36` this session showed it's a **maximum**-scan instead (seeded at `0xFFFF`, replaces only on a strictly larger key — the seed alone is structural proof of the intended direction, since a minimum-scan seeded there could never select anything). That correction resolves the item's original question: the already-documented post-hit key zero-out (disqualifying the just-hit target from being re-picked) only composes correctly with a maximum-scan — under the old, wrong minimum-scan reading it would have been self-defeating (the zeroed target would win every future comparison instead of losing). Seed-plus-side-effect together are stronger evidence of deliberate, finished design than "no dead arithmetic" alone. What can't be recovered from bytes is *why* sprite id specifically was chosen as the ranking key — retired as unprovable in principle, the same disposition as the item above.

⚠️ **A seventh untracked item, `UNKNOWN_random_mixer` (ranked item 25), is now CLOSED, `[PROVEN]` live in DOSBox** — same shape as items 20-22 above: it never had a registered entry in `docs/open-questions-history.md`, only an inline TODO in `gods-web/src/game/random.js` ("the MIXER is NOT ported"), where the port's random table came from a placeholder xorshift instead of `FUN_1000_2375`. Full disassembly plus a flag-flow trace of every call site prove the mixer is a pure 16-bit-seed function for the table generator's own 258 calls (`CF_in=0` at every one, each preceded by an `XOR`/`OR`/`CMP`/`AND` that clears it). Live-captured the real entry seed at `FUN_1000_37f6`'s entry (`[0x122]=0x6189`, live segment resolved by a `mem_scan` byte-signature match rather than trusted from an arbitrary pause) and the resulting 512-byte table; the disassembled algorithm reproduces it byte-for-byte from that seed. A genuine property of the original mixer fell out of this, deduced from the now-verified algorithm rather than separately observed live against `GAME.EXE` in this specific regime: any seed `< 128` degenerates into a pure doubling sequence for several draws (the high byte being 0 collapses the whole `RCR`/`XOR` chain), narrow enough that a live wall-clock seed almost never hits it but common enough that three of `gods-web`'s own tests — seeded with small constants for readability — were quietly relying on its low diversity. A brute-force sweep of all 65536 inputs through the JS port confirms exactly one seed maps to 0 under a single mix (0 itself), which makes the companion hang claim rigorous rather than merely plausible: since only 0 can ever produce 0, a chain started from any nonzero seed can never collapse to an all-zero table, so `FUN_1000_37f6`'s own infinite-retry hang really is reachable only from a boot whose BIOS tick count is exactly 0, not from some wider unquantified "small seed" range.
